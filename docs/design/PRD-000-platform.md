## Problem and users

Teams already have vendor desktops, open-source conductors and GitHub Agent HQ; the problem is not the absence of parallel-agent UI. The narrower unmet job is a customer-hosted, cross-vendor team control plane with auditable, per-repo policy and change gates in its open edition. This is a MED-confidence gap inferred from competing feature coverage, not an uncontested market (VISION §The one-paragraph thesis; R1 §Analysis; R3 §C).

1. **Platform / DevEx teams, audience 1, payer.** Job: deploy one team service inside the company boundary; let several teams use more than one agent and repo without giving agent runners merge authority; configure policy, budgets and audit from one place. **Real, MED:** comparable vendors monetise governance, but named platform teams built in-house rather than bought. SSO/SCIM, enterprise audit export and HA are later, not an assertion that the three-month alpha meets procurement needs (VISION §Who it is for; R1 §Recommendations; R3 §A).
2. **Engineering teams of 10 to 500, audience 2, user and adoption funnel.** Job: start two agents against separate checkouts, observe their work, review the resulting diffs and reach a gated PR with minimal manual orchestration. **Real but contested, MED:** teams pay for shared tools, while free OSS servers and bundled vendor surfaces limit willingness to pay. No migration wave is presumed (VISION §Who it is for; R1 §Recommendations; R3 §A).
3. **B2B2B embedders, audience 3, later channel.** Job: add an agent-conductor capability to a customer-facing product without building the task, runner and gate layer. **Not evidenced, LOW:** no direct buyer found in R1. Split 3a, agent-product startups for whom orchestration UX is the differentiator, **MED** reason to exclude at launch from R3 §A; 3b, forges, developer portals, sandbox/model vendors or consultancies for whom it is not the differentiator, **LOW** prospective channel requiring direct letters of intent. The P0 headless team API is not an embeddable, multi-customer product (VISION §Who it is for; R1 §5; R3 §A, §G).

## Goals and non-goals

1. **Goal:** A single customer-operated organisation can complete task -> run -> diff -> SHA-bound human gate -> PR using only the Apache-2.0 core, with a thin CLI and headless team API. No Enterprise licence is needed. (VISION §Design principles; R3 §B)
2. **Goal:** Give platform operators one per-org/per-repo configuration surface for allowed agents, execution tiers, tools, budgets, reviews and audit, without conflating worktrees with security sandboxes. (VISION §Design principles; R2 §Analysis)
3. **Goal:** Validate neutrality with two usable agent adapters and two executors, not a promise of parity or a large certified-provider matrix. (VISION §Strategy; R2 §Three-month scope)
4. **Goal:** After launch, measure R3 §G indicators on opt-in instances, report the opt-in rate, and apply the day-90 rule: activation at least 40%, multi-adapter share at least 20%, and at least two paid pilots to continue; one miss buys 30 days, two misses require re-scoping. These are business checkpoints, not acceptance tests for the 12-week alpha. (VISION §How we will know; R3 §G)
5. **Non-goal:** Build a coding agent, IDE, general workflow engine, sandbox provider, or better desktop-only conductor UI. (VISION §What it is NOT)
6. **Non-goal:** Prove a B2B2B buyer, promise hostile-code isolation in a container, or claim compliance/zero exfiltration during the alpha. (VISION §Who it is for; R2 §1, §Three-month scope; R3 §A)

## P0 scope

**Release definition:** A 12-week, single-org self-hosted alpha for one supported runner OS/architecture, after approved HLD/LLD/plan and R3 §G validation. One customer-operated product binary in server/runner modes plus Postgres in a documented Compose deployment, with at least one outbound self-hosted runner; a thin CLI client and a headless API; two production-path agent adapters; `trusted-local` worktrees and a hardened container executor; at most two Git hosts; one auditable per-org/per-repo policy schema; shared runs, diffs, human approval, checks and PR creation. All of this is Apache-2.0 core. This is a bounded product promise, not a claim of 1.0, HA, air-gap or enterprise readiness (VISION §Strategy, §Design principles; R2 §Three-month scope; R3 §B, §D).

**Boundary choices still subject to pilot evidence:**

1. **Client surface for the first release (R3 §D; VISION §Strategy).**
   - **Option A, thin CLI plus API (provisionally preferred).** Pros: small surface for team workflow and automation; deploys without a native desktop release. Cons: [ADVISORY] fewer visual review conveniences than desktop. Why preferred: bounded alpha engineering; the product value is gates, not a new UI.
   - **Option B, thin desktop plus API.** Pros: familiar parallel-agent review UI. Cons: [ADVISORY] native packaging and UI consume the bounded alpha; [ADVISORY] no CLI-first automation for a headless team. Why preferred if visual pilot feedback dominates: it avoids a separate review client; otherwise not preferred because it costs time without improving policy evidence.
   - **Verdict from BLOCKING alone:** neither option has a blocking con; both survive. CLI is an advisory sequencing preference, not a claim that desktop cannot work.

2. **First agent pair (R2 §2, §Three-month scope; R3 §G item 7).**
   - **Option A, Claude Code CLI and Codex CLI, both through permitted API-key/enterprise paths (provisionally preferred).** Pros: two independently operated vendors and documented noninteractive events. Cons: [ADVISORY] vendor terms or CLI event changes may require a substitution; [ADVISORY] both may depend on external inference. Why preferred: directly tests cross-vendor use if written vendor checks permit it.
   - **Option B, one permitted proprietary CLI and one open harness such as OpenCode.** Pros: avoids depending on two proprietary integration policies; permits a customer-chosen endpoint. Cons: [ADVISORY] a weaker test of two proprietary vendor adapters; [ADVISORY] capability parity still varies. Why preferred if vendor approval changes: it keeps two permitted harnesses in scope; otherwise it is the pre-agreed fallback to A.
   - **Verdict from BLOCKING alone:** both are viable when their permitted billing paths are available; no present BLOCKING con ranks them. If the written check rules out an integration, that specific integration becomes [BLOCKING] for that pair and B is used; neither consumer subscription auth nor undocumented permissions are prerequisites.

3. **Git-host breadth (R1 §5; R2 §Three-month scope; R3 §C).**
   - **Option A, GitHub plus GitLab (provisionally preferred).** Pros: demonstrates a non-GitHub PR path; addresses the named host-neutral gap. Cons: [ADVISORY] second-host integration and status mapping cost time. Why preferred: validates that the control plane is not tied to a single host.
   - **Option B, GitHub only initially.** Pros: simplest pilot for a GitHub-only partner. Cons: [ADVISORY] host neutrality remains an untested interface claim; [ADVISORY] narrower adoption. Why preferred if pilot demand is GitHub-only: cheapest way to validate the gated workflow; otherwise weaker evidence of host neutrality than A.
   - **Verdict from BLOCKING alone:** both survive; the second host is a conditional alpha target, not a reason to miss the core gate. Pilot evidence chooses the supported pair before HLD approval; never exceed two Git hosts in this slice.

4. **Lower-trust execution default (R2 §1, §Open questions, §Three-month scope; VISION §Design principles).**
   - **Option A, hardened self-hosted container; separate checkout and scoped credentials (provisionally preferred for controlled pilot code).** Pros: deployable alongside the Compose team server. Cons: [ADVISORY] shared kernel and egress misconfiguration limit the assurance available to a controlled pilot; [ADVISORY] hardening requires a threat review. Why preferred: fits the controlled pilot if its trust tier permits containers.
   - **Option B, microVM or external VM provider as the default.** Pros: stronger kernel boundary for hostile code. Cons: [ADVISORY] infrastructure/provider lifecycle and cost exceed the bounded alpha; [ADVISORY] stronger isolation still is not zero exfiltration. Why preferred if the pilot requires hostile-code kernel separation: stronger boundary; otherwise not preferred until that tier is measured.
   - **Verdict from BLOCKING alone:** for the declared controlled-pilot trust tier, neither option has a BLOCKING con, so both survive. If later evidence establishes a hostile-code boundary outside the hardened container's threat model, claiming Option A meets that new requirement becomes [BLOCKING]; HLD must then change executor scope or limit eligible jobs, not relabel a container as a VM. Unsandboxed worktrees are never the lower-trust option.

**Guardrail:** The R2 B-versus-E runner-plumbing spike, durability design, policy engine and provider contracts are HLD decisions, not extra PRD architecture verdicts. R2 eliminates standalone local-only A and hosted-control-plane-first D by BLOCKING team/self-host invariants; B, C and E remain viable (R2 §Reference architectures and options analysis).

## Functional requirements

Priority is release-relative: **P0** must pass before the 12-week alpha, **P1** is a post-alpha extension or a partner-dependent stretch, and **P2** is a later hypothesis. Each acceptance line describes a tester-observable check, not an implementation mandate. All P0 requirements run without the commercial module (VISION §Design principles; R3 §B).

1. **FR-1 (P0): Create a task for a configured repo using the team API and thin CLI.** Accept: an authorised member creates a task and retrieves its durable ID and initial state from both surfaces. Trace: VISION §Design principles; R2 §Analysis.
2. **FR-2 (P0): Start a run from a task, select an eligible agent and executor, and expose ordered progress until terminal state.** Accept: two simultaneous tasks show distinct run IDs, ordered events and independent outcomes to a second authorised user. Trace: VISION §Who it is for, §Design principles; R2 §Three-month scope.
3. **FR-3 (P0): Make the task -> run -> diff -> gate -> PR path complete in the Apache-2.0 edition.** Accept: a fresh unlicensed installation opens a PR after SHA-bound human approval and any required pre-PR checks, then keeps merge ineligible until any PR-triggered required checks on that same SHA pass, without Enterprise code. Trace: VISION §Design principles; R3 §B.
4. **FR-4 (P0): Install two production-path coding-agent adapters, each driven through a supported local CLI interface.** Accept: both configured agents produce event streams and diffs in the test repo, each on the local CLI worktree path and container executor, using permitted API-key or enterprise credentials. Trace: VISION §Strategy; R2 §Three-month scope.
5. **FR-5 (P0): Advertise and enforce per-agent capabilities rather than assume identical interactions.** Accept: an unsupported resume, steering or approval request is shown as unavailable or denied, never silently reported as successful. Trace: VISION §Design principles; R2 §Analysis.
6. **FR-6 (P0): Support API-key and enterprise-billing credential paths for each shipped agent; do not require consumer-subscription login.** Accept: each shipped adapter completes a run on a permitted non-consumer billing path with subscription login disabled. Trace: VISION §Design principles; R2 §2; R3 §C.
7. **FR-7 (P1): Where an agent supports ACP natively or through a verified adapter, ingest its session, event and tool-permission capabilities without equating ACP permission with merge approval.** Accept: an ACP fixture presents a permission request while a separate change gate remains pending. Trace: R2 §2; VISION §Design principles.
8. **FR-8 (P1): Offer policy-scoped MCP tools only for agents whose adapter declares MCP support; MCP is not the team task or gate protocol.** Accept: a permitted MCP tool is available in a test run, a forbidden tool is denied, and the task/gate records stay in the team API. Trace: R2 §2; VISION §Design principles.
9. **FR-9 (P0): Give every run a separate checkout and branch; prevent two active runs from writing one checkout.** Accept: concurrent runs edit the same filename without crossing changes or reusing the same writable checkout. Trace: VISION §Design principles; R2 §1, §Analysis.
10. **FR-10 (P0): Expose unsandboxed worktree runs as `trusted-local` only, never as secure execution isolation.** Accept: the API/CLI displays the trust label before dispatch and rejects a policy requiring sandboxing when worktree-only execution is selected. Trace: VISION §Design principles; R2 §1.
11. **FR-11 (P0): Provide a hardened self-hosted container executor for policy-eligible lower-trust runs, separate from the `trusted-local` worktree executor.** Accept: a sandbox-required run executes in a container with a separate checkout, without a host checkout, host agent credential or daemon socket mount. Trace: VISION §Design principles; R2 §1.
12. **FR-12 (P0): Support an outbound customer-operated runner that receives work without exposing inbound runner control ports.** Accept: a connected runner executes a queued task; while all eligible runners are disconnected, an unclaimed task remains queued. Trace: VISION §Strategy; R2 §Reference architectures and options analysis.
13. **FR-13 (P0): Permit a member to request cancellation and observe a terminal or explicitly unresolved run state.** Accept: cancelling an active run prevents new tool work and records cancellation or a named reconciliation state in the shared view. Trace: R2 §Three-month scope.
14. **FR-14 (P0): Survive runner/server restart and ambiguous dispatch without silently creating a second active writer.** Accept: forced runner death and duplicate delivery preserve one run record; unfinished work resumes safely or becomes `needs_reconciliation`. Trace: R2 §Three-month scope.
15. **FR-15 (P0): Show a diff and the exact candidate commit SHA before review.** Accept: the reviewer opens a run and sees the proposed files, diff and SHA captured for the gate. Trace: VISION §Design principles; R2 §Three-month scope.
16. **FR-16 (P0): Bind approval and required checks to that candidate SHA and fail closed on missing, failed, stale or errored gates.** Accept: a changed commit or missing approval blocks PR creation; a missing, failed or stale required check or gate error blocks PR creation or merge eligibility as appropriate. Trace: VISION §Design principles; R2 §Analysis.
17. **FR-17 (P0): Require a distinct authorised human to approve a change; execution identities cannot self-approve or merge.** Accept: the runner identity cannot approve its gated change or merge; an authorised human reviewer can approve. Trace: VISION §Design principles; R2 §Analysis.
18. **FR-18 (P0): Create a PR after the SHA-bound human change gate and surface host-side merge/check status without bypassing branch protections.** Accept: an approved candidate passing required pre-PR checks opens one PR; PR-triggered checks on its latest SHA must pass before merge eligibility, and a new SHA invalidates earlier approval. Trace: VISION §Design principles; R2 §Three-month scope.
19. **FR-19 (P0): Ship a tested PR path for at least one Git host.** Accept: a pilot repo on the chosen supported host passes the end-to-end FR-3 test. Trace: R2 §Three-month scope.
20. **FR-20 (P1): Add a second Git-host PR path if the pilot confirms the demand and scope, capped at two hosts in the first slice.** Accept: the same FR-3 scenario passes on GitHub and a non-GitHub supported host without changing the gate rules. Trace: R2 §Three-month scope; R3 §C.
21. **FR-21 (P0): Allow an org administrator to configure per-org and per-repo agent, executor, tool, network, time/concurrency, approval and check rules.** Accept: different repo policies in one org cause the same proposed run or change to receive different recorded allow/deny outcomes. Trace: VISION §Design principles; R3 §B.
22. **FR-22 (P0): Deny privilege transitions when policy evaluation or audit recording fails.** Accept: with policy evaluation unavailable or the audit write rejected, a run cannot gain tools or pass a change gate. Trace: VISION §Design principles; R2 §Analysis.
23. **FR-23 (P0): Keep an append-only, queryable basic audit trail in the open core for task, run, permission, policy, approval and PR decisions.** Accept: an authorised operator reconstructs actor, action, decision, reason, policy version, candidate SHA and ordering for a completed run. Trace: VISION §Design principles; R3 §B.
24. **FR-24 (P0): Enforce hard execution time and concurrency ceilings at run and repo/org scope.** Accept: a run past its time limit stops, and an excess concurrent run remains queued rather than executing. Trace: VISION §Design principles; R2 §Three-month scope.
25. **FR-25 (P0): Configure org/repo monetary warning thresholds and display best-effort usage with clear unknowns, not guaranteed dollar caps for opaque subscription billing.** Accept: a priced run crossing its configured threshold warns the operator; an agent with no priced usage data displays `unknown` and does not claim a guaranteed dollar ceiling. Trace: VISION §Design principles; R2 §Analysis.
26. **FR-26 (P0): Provide single-org admin, submitting member and human reviewer permissions, with an execution identity that has no review/merge role.** Accept: an unauthorised user cannot change policy or approve; an admin can change policy; a reviewer distinct from the runner can decide a gate. Trace: VISION §Design principles; R3 §B.
27. **FR-27 (P0): Expose the complete team workflow through an authenticated headless API, independent of a desktop session.** Accept: a scripted client creates a task, observes a run, reads a diff, records a human approval and retrieves the PR through documented API operations. Trace: VISION §Strategy; R2 §Three-month scope.
28. **FR-28 (P0): Supply a thin CLI for the primary team workflow rather than a second server-side source of truth.** Accept: the CLI starts and cancels a run, shows its diff/gate state and links to its PR, with results matching API reads. Trace: VISION §Strategy; R3 §D.
29. **FR-29 (P0): Define versioned extension boundaries for agents, executor providers, policy gates, roles and presentation metadata without running untrusted plugins in the server.** Accept: an unsupported extension version is rejected and an unknown executor cannot obtain server privileges by registering itself. Trace: VISION §Design principles; R2 §Analysis.
30. **FR-30 (P1): Add operator-facing branding through the core's versioned presentation extension, without a fork, in a later Enterprise release.** Accept: an Enterprise theme changes displayed name and colours on a test instance without patching core, while an unlicensed core instance cannot enable the commercial branding controls. Trace: VISION §Design principles; R2 §4; R3 §B.
31. **FR-31 (P0): Install the server, Postgres and runner via a single documented Compose deployment.** Accept: on the supported host, a new operator runs the documented Compose command and completes a first run without any separate workflow-engine cluster. Trace: VISION §Design principles; R2 §Analysis.
32. **FR-32 (P0): Make opt-in usage heartbeat explicitly disabled by default and disclose every field transmitted.** Accept: a fresh install emits no product telemetry; an opted-in test instance reports activation and adapter-use counters with its opt-in status visible. Trace: VISION §How we will know; R3 §B, §G.
33. **FR-33 (P2): Expose a customer-embedding contract only if 3b buyer interviews validate a distinct need; do not confuse it with FR-27.** Accept: before any P2 build is committed, R3 §G item 4 records at least two letters of intent from the 3b audience. Trace: VISION §Who it is for, §Open questions; R3 §A, §G.
34. **FR-34 (P0): Authenticate users of a single organisation without depending on Enterprise SSO; provide the core OIDC path described in R3.** Accept: a configured OIDC member signs in and can call the API within their role, while an unknown identity is denied. Trace: R3 §B; VISION §Design principles; R2 §Analysis.

## Non-functional requirements

These are alpha targets, not externally validated service-level agreements. R2 §1 supplies only provider **boot/start** claims, not end-to-end prompt-ready or diff-ready benchmarks; no subsecond workload latency target is inferred from those claims.

1. **NFR-1 (P0), install time:** On a supported host with container runtime, runner resources, Git access, permitted agent credentials and the documented Compose prerequisites ready, an operator should reach the first successful run within **60 minutes**. This is the LOW-confidence VISION onboarding hypothesis, scoped to an initial run rather than SSO, production security review or first PR. Accept: a fresh installation with documented prerequisites ready reaches the first successful run in at most 60 minutes; log elapsed time and failures, and revisit the target if pilots contradict it. Trace: VISION §The one-paragraph thesis, §Open questions item 3; R2 §Open questions.
2. **NFR-2 (P0), latency evidence:** Record cold and warm `queued -> checkout ready -> sandbox ready -> agent ready to prompt` durations separately under representative pilot repo sizes; publish median and tail observations before claiming a target. No numerical ready-to-prompt or PR latency SLO is justified by R2 provider boot claims. Accept: a pilot run report contains each stage and distinguishes worktree from container cold/warm runs, without quoting provider start latency as agent-ready latency. Trace: R2 §1, §Three-month scope, §Open questions.
3. **NFR-3 (P0), recoverable availability:** One failed or restarted server/runner must not silently lose a task, duplicate an active checkout writer or auto-pass a gate; this single-node alpha makes no 99.9%/HA claim. Accept: forced server restart, runner death and duplicate dispatch either recover a safe run or expose `needs_reconciliation` and keep merge ineligible. Trace: R2 §Analysis; VISION §Design principles.
4. **NFR-4 (P0), execution isolation:** Unsandboxed worktrees are available only under the visible `trusted-local` label; a sandbox-required policy must enforce separate hardened container execution with scoped secrets and without host credential/checkout or Docker socket mounts. Containers share the kernel and are not a microVM or an arbitrary-hostile-code guarantee. Accept: an adversarial policy test rejects a `trusted-local` request when sandboxing is required and verifies forbidden host mounts/secrets are inaccessible to the container. Trace: R2 §1, §Analysis; VISION §Design principles.
5. **NFR-5 (P0), authorisation and confidentiality:** Scope user, Git and runner credentials to their roles and repos; prevent an agent or compromised runner from gaining approval/merge authority; redact sensitive material from basic audit events and disable outbound product telemetry by default. Model-provider requests and a user-permitted agent tool are explicitly **not** an air-gap claim. Accept: a runner credential fails admin/approve/merge API calls and secret strings do not appear in an ordinary audit record. Trace: VISION §Design principles; R2 §Analysis; R3 §B, §F.
6. **NFR-6 (P0), first-release tenancy:** One customer-operated instance serves one organisation with multiple teams, users and repos; role and repo boundaries hold within that organisation, but hostile-customer multi-org isolation is not offered. Accept: a user without permission for a repo cannot read its runs or audit records through API/CLI even when the instance serves another team. Trace: VISION §Design principles; R3 §B.
7. **NFR-7 (P0), bounded operating cost:** Default to customer-operated runner/compute, require no paid hosted sandbox or usage-metered self-host licence, enforce configured hard time/concurrency caps and label vendor-token or external-provider costs as estimates when not observable. Accept: an instance completes the core workflow with no paid sandbox account and refuses a run above its configured concurrency cap. Trace: VISION §Strategy, §Design principles; R2 §1, §Analysis; R3 §B, §D.
8. **NFR-8 (P0), upgradeability:** Persist runs, policies and audit across a documented schema-compatible upgrade, with database backup/restore and a documented rollback boundary; no promise of zero-downtime migrations. Accept: back up a populated alpha instance, upgrade it, verify a prior run and gate decision, and restore it from the backup in a test environment. Trace: R2 §Analysis; VISION §Design principles.
9. **NFR-9 (P0), compatibility and licensing:** Apache-2.0 core deployment must function without Enterprise binaries or required non-OSI-licensed workflow servers; dependencies and optional external backends must be reviewed against the approved core boundary. Accept: a clean Compose installation with no Enterprise licence and no separately installed workflow cluster passes FR-3. Trace: VISION §Strategy, §Design principles; R2 §Analysis; R3 §B.
10. **NFR-10 (P0), audit integrity and retention:** Policy/privilege transitions require a committed, ordered and reconstructable audit event; optional full prompt/tool payloads must not be necessary for the basic audit trail. Accept: simulate failed audit persistence during approval and verify both denial and an operator-visible error without emitting an approved state. Trace: VISION §Design principles; R3 §B.

## Out of scope

1. **Hosted edition and vendor-managed control plane:** after self-hosted proof and paying customers, under a subsequent hosted product PRD/HLD (VISION §Strategy; R3 §B, §D). Customer-side workers alone do not count as self-hosting the control plane (R2 §2).
2. **Embeddable B2B2B/white-label surface:** after the 3b direct-conversation test, under a subsequent embedder product PRD and tenancy HLD; FR-27 is an internal team API, not a customer-tenant API (VISION §Who it is for, §Open questions item 7; R3 §A, §G item 4).
3. **Secure multi-org, multi-customer tenancy, end-customer quotas and metering:** later tenancy HLD after signed embedder evidence, not inferred from P0 single-org roles (VISION §Strategy; R2 §Analysis; R3 §A).
4. **Enterprise module contents:** later Enterprise product PRD and HLD for SSO/SCIM, multi-org RBAC, audit export, policy packs with approvals, HA, air-gap bundles, commercial branding, cross-vendor cost accounting and SLA. The P0 core still includes basic OIDC, single-org roles, local audit and declarative gates (VISION §Strategy; R3 §B; R2 §Three-month scope).
5. **Certified external sandbox-provider matrix and default microVM:** later execution/sandbox-adapter HLD, after pilot trust-tier evidence; an exploratory external provider spike does not create a shipped claim (VISION §Strategy; R2 §Three-month scope).
6. **Public, stable plugin marketplace or arbitrary untrusted server-side plugins:** later extension-point LLD/security review; the P0 contract supplies versioned boundaries only (VISION §Design principles; R2 §Analysis).
7. **Full desktop/mobile/IDE client, workflow-engine product and per-agent interactive parity:** later client/product requirements if validated; P0 remains a thin CLI on a team server (VISION §What it is NOT, §Strategy; R2 §2, §Three-month scope; R3 §D).
8. **Guaranteed dollar limits for opaque subscription agents, external compliance certifications and unconditional zero-exfiltration claims:** later financial-control and security product requirements only with verifiable billing and threat-model evidence; P0 offers hard runtime caps and best-effort monetary information (R2 §1, §Three-month scope; VISION §Design principles).
9. **Automatic merge as an agent privilege:** excluded from this product by the human-gate/host-protection invariant; any later merge automation requires a separate policy-and-gates HLD and must retain separate human/host authority (VISION §Design principles; R2 §Analysis).
10. **A public product name:** R3 §E naming/trademark clearance and maintainer reservation, not the PRD or an alpha runtime feature (VISION §Strategy; R3 §5, §E).

## Assumptions

An assumption is not a discovered fact. If false, revisit the listed requirements and acceptance criteria before implementing. **UNRUN R3 §G** denotes an experiment required before HLD approval for which these approved inputs report no outcome; this PRD does not imply it was conducted (VISION §How we will know; docs/process/PHASE-1.md §Scheduled alongside Phase 1).

1. **A payer exists for the enterprise split [UNRUN R3 §G item 1, kill test].** If fewer than three non-binding design-partner letters or two named budget lines emerge from 10 to 15 platform/DevEx calls, drop the Enterprise-commercial premise and re-scope to the OSS team server or stop; the open workflow requirements remain contingent on that decision. (VISION §How we will know; R3 §G)
2. **Shared gates/audit solve a user need beyond existing OSS servers [UNRUN R3 §G items 2 and 6].** If interviews and issue-tracker mining do not support this, revisit the differentiation, FR-21 through FR-23 and pilot selection. (R1 §Analysis; R3 §G)
3. **Teams choose more than one agent in practice [UNRUN R3 §G items 2 and 3].** If pilots need one vendor only, FR-4 remains an architectural neutrality test but the multi-adapter business thesis and day-90 threshold need revalidation. (VISION §How we will know; R3 §G)
4. **The first two agents can be driven on explicitly permitted API-key or enterprise billing paths [UNRUN R3 §G item 7].** If a vendor rules out the chosen integration, replace that adapter with a permitted open harness rather than depend on consumer subscription auth. (VISION §Open questions item 2; R2 §2; R3 §G)
